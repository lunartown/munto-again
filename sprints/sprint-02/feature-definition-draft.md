# 기능 정의 초안 — 소모임 가입 전 판단

원자료: `interview-note-kimdain.md`, `interview-note-yangnabin.md`, `ia-somoim-current-state-draft.md`(SM-01~SM-16)

## 표기 규칙

이 문서는 두 층위를 구분해 적는다.

- **근거** — 인터뷰·과업에서 확인된 것. 등급을 함께 적는다.
  - `관찰` 과업 중 실제 행동으로 확인됨 (가장 강함)
  - `경험` 실제 겪은 일의 회상
  - `자기보고` 진술. 가정형이면 `자기보고(가정형)`으로 구분
  - `n/2` 두 참가자 중 몇 명에서 확인됐는지
- **결정** — 근거가 없어도 설계상 정해야 하는 것. 판단 이유와 뒤집힐 조건을 함께 적는다.
  - `근거 기반` 위 근거에서 직접 도출
  - `제약 기반` 데이터 구조·운영 구조상 다른 선택지가 막힘
  - `임의` 근거도 제약도 없이 정함. 먼저 재검토할 대상

근거가 없다는 이유로 결정을 미루지 않는다. 대신 어느 층위에서 정한 것인지 남긴다.

## F1. 활동 이력 요약

**사용자 질문** — "이 모임 지금도 진짜 굴러가나?"

| 칸 | 내용 |
|---|---|
| 관찰된 문제 | 김다인: 가입 인원은 있는데 채팅방이 비어 있는 "유령 모임"을 문제로 지목. 모임이 활발한지 볼 때 "몇 개의 일정을 진행했는지"를 확인한다고 답함 — `경험`+`자기보고`<br>양나빈: 모임을 볼 때 "활동이 주기적으로 되고 있는지"를 가장 먼저 봄 — `경험` |
| 근거 등급 | **S1 최근 활동 게시글 = 필수, 2/2 일치**. 두 참가자가 유일하게 완전히 일치한 항목 |
| 현재 화면 공백 | SM-02·SM-03 상세 홈탭의 정기모임 목록은 **D-day가 붙은 예정 정모만** 표시. 지난 개최 이력은 게시판(SM-05)·사진첩(SM-04)에 흩어져 있어 직접 세어야 함 |
| 기존 기능과 중복 | **부분 중복 — 차별점 명시 필요.** SM-07이 이미 "방금 대화"·"30분 전 대화"를 노출 중. 다만 이는 **채팅 발생 시점** 기준이라, 채팅만 활발하고 정모는 안 여는 모임을 활발해 보이게 만든다. 김다인이 지목한 유령 모임을 오히려 못 거른다. 이 기능의 축은 "대화"가 아니라 **"개최"** |
| 데이터 출처 | 서버에 이미 있음 (정모 개최 기록). 호스트 추가 입력 불필요 |

### 결정

| 항목 | 결정 | 층위 | 이유 |
|---|---|---|---|
| 표시 지표 | 최근 개최일 + 집계 기간 내 개최 횟수 | `근거 기반` | 김다인이 확인한다고 말한 것이 "몇 개의 일정을 진행했는지" = 횟수 |
| 평균 참석 인원 | 넣지 않음 | `근거 기반` | 정모 카드에 이미 "N명 참석중"이 있음(SM-02·SM-03). 중복 |
| 집계 기간 | 최근 3개월 | `임의` | 주기를 가늠할 수 있는 최소 구간으로 잡음. 사용자 근거 없음 |
| 배치 | 상세 홈탭, 정기모임 목록 **바로 위** | `근거 기반` | 김다인이 마지막으로 본 모임에서 "최근 활동 게시글이 잘 보였고, 그 아래 바로 정기모임 D-1/D-2가 직관적이어서 좋았다"고 긍정 평가한 순서와 동일 |
| 목록 카드 반영 | 넣지 않음 | `근거 기반` | 김다인이 목록 화면 밀도를 문제로 지목("뭘 눌러야 이동되는지, 이게 모집글인지조차 판단 어려움") |
| 개최 0회 모임 | 숨기지 않고 "최근 3개월 정모 없음"으로 표시 | `근거 기반` | 유령 모임을 **거르는 것**이 이 기능의 목적. 안 보여주면 판단할 수 없음 |

### 뒤집히면 무너지는 것

다음 참가자들이 활동성을 판단할 때 지난 개최 이력 대신 최근 대화 시점·게시글만 본다면 → 기존 SM-07 표시로 충분. 기능 폐기.

## F2. 지역 필터

**사용자 질문** — "이거 내가 갈 수 있는 데서 하는 모임 맞아?"

| 칸 | 내용 |
|---|---|
| 관찰된 문제 | 김다인: 과업 중 "내 지역 만들기"를 "더보기"로 오인. 지역을 선택했는데도 자기 동네가 안 떠서 "아까 지역 선택을 왜 한 거야?"라고 발화 — 필터가 실제로 반영되는지 확신하지 못함 — `관찰`<br>김다인: 당근이 전국으로 확대되며 종로구 모임이 노출되는 것에 이탈감. 거리를 최우선 기준으로 둠 — `경험`<br>김다인: 애초에 당근을 먼저 떠올린 이유가 이동 거리를 싫어해 동네 기반 서비스를 선호했기 때문 — `경험`<br>양나빈: 자유 회상 1순위가 "장소" — `자기보고` |
| 근거 등급 | **방향 2/2 일치** + 김다인 `관찰` |
| 현재 화면 공백 | SM-06·SM-09·SM-12·SM-16 — 필터 축이 전부 카테고리(대분류 탭 + 소분류 칩). 지역은 헤더 라벨(SM-01 "신림동")로만 존재하고 목록 결과에 걸리지 않음 |
| 기존 기능과 중복 | 없음. SM-06의 소분류 필터칩 패턴을 확장 |
| 데이터 출처 | 서버에 이미 있음 (모임 지역값). 호스트 추가 입력 불필요 |

### 검토했으나 채택하지 않은 형태

| 형태 | 기각 이유 |
|---|---|
| **카드에 거리 표시**(2.1km) | ① 모임의 등록 위치는 호스트가 플랫폼 요구에 맞춰 잡은 대표값이고, 정모 장소는 회차마다 다를 수 있음(SM-02·SM-03의 정모별 장소) — 없는 정확도를 주장하는 표시가 됨 ② 반복 참석형 모임에서 거리는 임계값이지 정렬 기준이 아님. 2.1km와 3.4km의 차이가 가입 결정을 바꾸지 않음 ③ 카드에 요소가 늘어 밀도 문제와 충돌 |
| **거리 기반 필터**(5km 이내) | 위 ①과 같은 부정확한 좌표를 쓰면서, 잘못 걸러진 모임이 아예 안 보여 오차가 드러나지 않음. 표시보다 위험함. 또한 사용자가 감을 갖는 단위가 아님 — 두 참가자의 불만이 모두 행정구역으로 표현됨("종로구가 뜬다", "내 동네가 안 뜬다") |
| **지역 탭**(우리동네 탭 등) | 범위가 제품이 정한 값으로 고정되어 사용자가 조정할 수 없음. 김다인의 문제는 **본인이 설정한 지역이 반영되지 않는 것**이라, 고정 탭은 이 문제를 건드리지 못함 |
| **"가까운 순" 정렬 탭** | 정렬은 제외를 하지 않음. 먼 모임이 목록 아래에 남아 스크롤하면 다시 노출됨 |

### 결정

| 항목 | 결정 | 층위 | 이유 |
|---|---|---|---|
| 지역 단위 | **구** | `제약 기반` | 김다인이 원한 것은 "내 동네"(동)에 가깝지만, 소모임의 모임 지역값이 구 단위로 존재함(카드 "관악구", 모임명 "(관악/동작/서초)", "OO구 클래스"). 동으로 거르면 결과 공급이 말라 "내 동네 모임이 안 뜬다"를 악화시킴 |
| 복수 선택 | 허용 | `근거 기반` | 모임 자체가 여러 구에 걸침("(관악/동작/서초) 플립보드게임"). 단일 선택이면 경계 거주자가 옆 구 모임을 못 봄. 김다인이 "더 가까운 다른 수영 모임"을 찾아 옮긴 것도 인접 탐색 |
| 선택 상한 | 3개 | `임의` | 무제한이면 필터가 무의미해지고 칩이 화면을 넘김. 근거 없음 |
| 인접 구 자동 포함 | **하지 않음.** 대신 인접 구를 추천 칩으로 제안하고 선택은 사용자가 함 | `근거 기반` | 자동 포함은 "내가 고르지 않은 것이 섞여 나온다"로, 김다인의 원래 불만과 같은 구조. 사용자가 고른 것만 나와야 필터를 신뢰함 |
| 기본값 | 가입 시 설정한 동이 속한 구 1개 | `근거 기반` | 빈 값으로 시작하면 첫 진입이 전국 목록이 되어, 김다인이 당근에서 겪은 상태와 같아짐 |
| 적용 상태 표시 | 선택된 구 칩을 목록 상단에 고정하고 결과 수를 함께 표시 | `근거 기반` | 김다인이 막힌 지점이 "걸었는데 걸렸는지 모르겠다"는 것 |
| 적용 화면 | 목록 더보기(SM-07·09·10·12·13·14), 카테고리 상세(SM-06), 검색 결과(SM-16) | `근거 기반` | 김다인이 지역 불일치를 겪은 곳이 목록 화면 |
| 카드 변경 | 없음 | `근거 기반` | 카드에 이미 지역 텍스트가 있어, 필터가 걸리면 그 표시가 확인 역할을 함. 밀도를 늘릴 필요 없음 |

### 뒤집히면 무너지는 것

다음 참가자들이 지역을 좁히지 않고 목록 전체를 훑는다면 → 우선순위 하향. 구 단위로 걸렀는데도 "같은 구인데 멀다"는 불만이 나온다면 → 지역 단위 결정 재검토.

## F3. 참여 조건 표면화

**사용자 질문** — "나 같은 사람이 가도 되나?"

| 칸 | 내용 |
|---|---|
| 관찰된 문제 | 김다인: 모임 상세에서 실력 조건 문구("선출이면 좋은데 팀 애송이라서", "고연차는 안 받네")를 직접 찾아 읽는 행동 — `관찰`<br>김다인: "마라톤에 진심인 분들, 초보도 환영"처럼 제목과 실제 성격이 어긋나 보이는 사례를 부정 평가 — `관찰`<br>양나빈: 배드민턴 급수 표기(A1)를 보고 무슨 뜻인지 몰랐음 — `관찰` |
| 근거 등급 | **양쪽 모두 과업 중 관찰된 행동** (S7 병합, 1/2 + 1/2). 자기보고가 아님 |
| 현재 화면 공백 | SM-02·SM-03 홈탭의 소개 텍스트가 자유 형식 한 덩어리. 김다인이 "화면 밀도가 높다"고 지목한 구간 |
| 기존 기능과 중복 | 없음 |
| 데이터 출처 | **호스트 입력 필요 — 이 기능의 최대 약점.** 소모임 모임장은 무보상으로 운영하므로 입력률이 위험 |

### 결정

| 항목 | 결정 | 층위 | 이유 |
|---|---|---|---|
| 데이터 확보 방식 | 개설 폼에 선택 입력 필드 추가 | `제약 기반` | 소개글 파싱은 호스트가 애초에 안 쓴 정보를 만들어낼 수 없음. 김다인이 읽은 실력 조건 문구도 일부 모임에만 있었음 |
| 필수 여부 | **선택 입력.** 미입력 시 "미기재"로 표시 | `근거 기반` | 무보상 운영 구조에서 필수 입력은 개설 이탈을 만듦. 그리고 "없음"도 판단 정보 — 양나빈이 급수 표기를 못 알아본 것처럼, 모르는 채 두는 것보다 없다고 아는 편이 나음 |
| 항목 | 초보 수용 여부 / 참가자 실력대 | `근거 기반` | 두 참가자에게서 관찰된 것이 이 둘 |
| 실력대 표기 | 급수·등급 코드 대신 서술형("입문 환영", "경험자 위주") | `근거 기반` | 양나빈이 "A1"을 이해하지 못함 |
| 배치 | 상세 홈탭, 소개 텍스트 위 | `근거 기반` | 소개글에 묻히는 것이 문제이므로 소개글보다 먼저 읽혀야 함 |

### 뒤집히면 무너지는 것

다음 과업에서 참가자들이 조건 확인 없이 가입을 결정한다면 → 우선순위 하향. 호스트 입력률이 낮게 나오면 → 데이터 확보 방식부터 재설계.

## 우선순위

| 순위 | 기능 | 근거 강도 | 데이터 리스크 |
|---|---|---|---|
| 1 | F1 활동 이력 요약 | 2/2 (유일한 완전 일치) | 없음 — 서버 보유 |
| 2 | F2 지역 필터 | 방향 2/2 + 관찰 | 없음 — 서버 보유 |
| 3 | F3 참여 조건 표면화 | 양쪽 관찰 | **있음 — 호스트 입력 필요** |

F1·F2는 근거와 데이터가 모두 확보돼 있고, F3는 근거는 강하나 데이터 확보 방식이 별도 과제로 남는다.

| 후보 | 제외 이유 |

| **모임 비교 기능** | 페르소나의 "왕복 3회 미만"이 `0/2` 완전 가설. 멘토가 제시한 확인 항목 5번이 정확히 이것이며 아직 미확인 |
| **온보딩 관심사 반영 / 정렬 개선** | 김다인의 가장 큰 불만이나 추천 로직 문제라 화면 설계로 풀리지 않음. Sprint 02 범위(가입 전 판단)와 단계가 다름 |
| **모임장 신뢰 정보** | 가입 **전에** 모임장 정보를 확인했다는 관찰이 0건. 김다인의 방장 약속 불이행은 가입 후 이탈 원인이고, 양나빈의 다단계는 개인 연락으로 벌어진 일. S11 호스트 스타일은 김다인 "없어도 상관없음" / 양나빈 "있으면 좋음"으로 갈림 |

### 안전 — 미해결로 남김

문제로는 강하다. 즉시 제외 조건 `2/2` 일치이고, 양나빈에게는 실제 피해 경험(오픈채팅 독서모임 → 개인 연락 → 다단계)이 있다.

그런데 **가입 전에 화면에서 무엇을 보고 안전을 판단하는지에 대한 관찰 근거가 없다.** 양나빈이 안전 확인으로 든 세 가지 중 "활동이 주기적으로 되고 있는지"는 F1이, "순수하게 취미를 하는 곳인지"는 F3가 부분적으로 답한다. 남는 것은 유해한 접근에 대한 것인데, 이는 화면 정보로 풀리지 않고 플랫폼 심사·인증이 필요하다. 소모임은 모임장이 무보상으로 운영하는 구조라 플랫폼이 개별 모임을 심사할 사업적 유인이 약하다.

근거 없이 기능을 만들면 앞서 기각한 "모임장 신뢰 정보"와 같은 오류가 된다. **다음 과업 테스트의 관찰 항목에 "안전을 판단할 때 화면에서 실제로 무엇을 봤는가"를 넣고, 그 결과가 나온 뒤 기능화 여부를 정한다.**

1. 활동성을 판단할 때 실제로 무엇을 보는가 — 지난 개최 이력인가, 최근 대화·게시글인가 (F1 반증)
2. 목록에서 지역을 좁히는가, 전체를 훑는가. 구 단위로 충분한가 (F2 반증)
3. 조건 확인 없이 가입을 결정하는가 (F3 반증)
4. **안전을 판단할 때 화면에서 무엇을 보는가** (미해결 항목)
5. 상세 정보만으로 결정하는가, 여러 모임을 오가며 비교하는가 (비교 기능 판단)

표본 조건은 김다인 쪽으로 맞춘다 — 사회초년생 직장인 + 실제 모임 참석 경험. 현재 두 참가자의 답이 갈리는 항목들이 성향 차이인지 표본 차이(경험자/미경험자, 직장인/학생)인지 구분되지 않는다.
