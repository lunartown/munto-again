# Sprint 1.5 — 문토 Current-State Audit

> 상태: 진행 중 — 1차 캡처·플로우·근거 매핑 완료, 미확인 상태 보강 중
> 목적: Sprint 1의 문제 정의를 문토의 현재 화면·정보·사용자 흐름에 연결하고, Sprint 2에서 다룰 리뉴얼 범위를 결정한다.  
> 전제: 이 단계는 새로운 문제를 찾는 추가 리서치가 아니라, 문토 리뉴얼을 위한 현재 상태 분석이다.

## 1. 왜 필요한가

Sprint 1에서 다음 문제를 확인했다.

> 사용자는 클럽에 가입하기 전에 활동 목적·반복 방식·구성원 분위기·운영
> 규칙·최근 활동 이력을 비교하기 어렵다.

하지만 이 문제만으로는 어떤 화면을 어떻게 바꿔야 하는지 결정할 수 없다. Sprint 1.5에서는
문토의 현재 플로우에서 사용자가 어떤 정보를 보고, 어떤 행동을 하며, 어느 순간에 판단을
멈추는지 확인한다.

## 2. 분석 목표

1. 문토에서 클럽을 처음 고르는 사용자의 현재 여정을 재현한다.
2. 각 단계에서 제공되는 정보와 제공되지 않는 정보를 기록한다.
3. Sprint 1의 인터뷰·리뷰 근거를 현재 플로우의 문제 지점에 연결한다.
4. 문토가 통제할 수 있고 Sprint 2 화면으로 구체화할 수 있는 문제를 우선순위화한다.
5. 하나의 핵심 시나리오와 최소 기능 범위를 정한다.

## 3. 분석 범위

### 3.1 우선 여정

```text
클럽 탐색
  → 검색·필터
  → 클럽 상세 확인
  → 활동 적합성·운영 지속성 판단
  → 가입 질문
  → 승인·가입 완료
  → 채팅·정기 활동
```

### 3.2 보조 여정

아래 흐름은 현재 구조를 이해하기 위해 표시하되, Sprint 2의 핵심 화면 범위에는 넣지 않는다.

- 소셜링·챌린지의 상세 참여 흐름
- 클럽 개설·운영자 정보 입력
- 후기·평점 작성
- 취소·환불·신고·퇴출
- 문제 발생 후 처리 상태 확인

### 3.3 이번 단계에서 제외

- 문토 전체 앱의 모든 화면 분석
- 추천 알고리즘의 내부 로직 추정
- 소개팅·파티 모임의 제거 여부 결정
- 경쟁 서비스의 기능을 그대로 복사하는 벤치마크
- 아직 확인하지 않은 기능을 현재 사실처럼 기록

## 4. 조사 방법

### 4.1 현재 플로우 캡처

실제 문토 앱 또는 웹에서 신규 사용자의 관점으로 다음 행동을 수행한다. 2026-08-02에
소셜링·클럽·챌린지·홈·검색·카테고리·찜 화면을 우선 캡처했으며, 캡처 파일은
`../../archive/research/data/current_state/screenshots/`에 보존했다.

1. 지역과 관심사를 정하지 않은 상태에서 목록을 연다.
2. 클럽 검색·필터·정렬로 후보를 좁힌다.
3. 클럽 후보 2~3개의 상세 페이지를 비교한다.
4. 가입 질문과 활동비가 있는 경우의 결제 직전까지 진행한다.
5. 승인·가입 완료·채팅·정기 활동 화면이 어디에서 이어지는지 확인한다.

실제 확인이 어려운 단계는 `확인 필요`로 표시하고, 추정으로 채우지 않는다.

### 4.2 화면·정보 인벤토리

| 단계 | 화면/컴포넌트 | 사용자가 보는 정보 | 사용자의 행동 | 확인 상태 |
|---|---|---|---|---|
| 탐색 | 클럽 목록·카드 | 제목, 카테고리, 전체 멤버 등 | 후보를 고른다 | 부분 확인 — CS-01, 30~31, 50 |
| 검색 | 클럽 검색·필터·정렬 | 지역, 온라인 여부, 정렬 등 | 조건을 바꾼다 | 확인 — CS-31~35 |
| 상세 | 클럽 상세 | 소개, 멤버, 관련 활동, 댓글 | 가입 여부를 판단한다 | 확인 — CS-36 |
| 가입 | 가입 질문·활동비 | 커스텀 질문, 유료인 경우 결제·환불 | 답변하고 가입을 요청한다 | 확인 — CS-37~38 |
| 승인 | 가입 대기·완료 | 승인 상태, 자동 취소, 채팅 진입 | 대기하거나 클럽에 들어간다 | 확인 — CS-39~41 |
| 반복 활동 | 채팅·소셜링 탭 | 정기 활동 일정·변경 공지 | 활동을 확인하고 참여한다 | 부분 확인 — CS-41~42 |

`미확인`은 실제 앱을 확인한 뒤 화면명, 캡처 날짜, 확인 방법으로 갱신한다. 현재까지
CS-01~CS-62 번호를 부여했고 실제 파일은 39장이다. 참석·체크인·후기 완료 화면과
챌린지 전용 대기·환불 화면은 아직 확보하지 않았다.

### 4.3 문제·근거 매핑

Sprint 1의 근거 카드는 플로우 단계에 다음 형식으로 연결한다.

| 플로우 단계 | 현재 문제 | 사용자 행동/결과 | 근거 카드 | 근거 강도 |
|---|---|---|---|---|
| 탐색 |  |  |  | 확인 필요 |
| 검색·필터 |  |  |  | 확인 필요 |
| 상세 |  |  |  | 확인 필요 |
| 가입 질문·활동비 |  |  |  | 확인 필요 |
| 승인·채팅 |  |  |  | 확인 필요 |
| 참석·후기 |  |  |  | 확인 필요 |

근거 표기 규칙:

- 인터뷰: `U02-01`, `HU02-06`처럼 카드 ID를 사용한다.
- 리뷰: `OCR031`, `ASR038`처럼 원문 ID를 사용한다.
- 모집글: 목록 분석의 분류·카테고리 수치를 사용한다.
- 현재 화면에서 직접 확인하지 못한 연결은 `가설`로 표시한다.

## 5. Current Flow 작성 규칙

FigJam에 현재 플로우를 그릴 때 각 단계에 다음 정보를 함께 표시한다.

- 시작 조건: 사용자가 어떤 상태에서 진입하는가
- 화면: 실제 화면명 또는 캡처 번호
- 행동: 사용자가 무엇을 누르거나 입력하는가
- 판단 정보: 선택에 필요한 정보가 무엇인가
- 상태 변화: 가입 요청·승인·가입 완료 등 어떤 상태가 바뀌는가
- 이탈/막힘: 사용자가 멈추거나 외부 채널로 이동하는가
- 근거: 인터뷰·리뷰·모집글 ID
- 확인 상태: 확인됨 / 부분 확인 / 가설 / 미확인

현재 플로우와 개선 플로우를 같은 보드에 섞지 않는다. Sprint 1.5에서는 `현재 상태`만
작성하고, 아이디어와 개선안은 별도 영역에 둔다.

## 6. 분석 질문

### 사용자의 선택

- 사용자는 목록에서 후보를 고를 때 무엇을 근거로 삼는가?
- 클럽의 실제 활동 목적과 구성원 분위기를 어디에서 판단하는가?
- 후보를 비교할 수 있는 정보 구조가 있는가?

### 정보의 충분성

- 활동 주기·최근 활동·활성 멤버 정보가 어디에 흩어져 있는가?
- 음주·촬영·연령·신규 참여 방식·운영 규칙을 빠르게 확인할 수 있는가?
- 정보가 있어도 클럽 간 비교가 가능한 형태인가?

### 플랫폼의 책임 경계

- 신청·결제 이후 사용자가 어떤 상태를 확인할 수 있는가?
- 문제 발생 시 책임 주체와 처리 상태가 현재 플로우에 드러나는가?
- 호스트에게만 맡겨진 운영 행동은 무엇인가?

## 7. 우선순위 결정 기준

각 문제를 다음 기준으로 1~3점 평가한다.

| 기준 | 1점 | 2점 | 3점 |
|---|---|---|---|
| 사용자 영향 | 불편이 작음 | 선택을 지연시킴 | 포기·불신·손실로 이어짐 |
| 근거 강도 | 연구자 해석 | 한 자료에서 반복 | 인터뷰·리뷰·현재 화면에서 교차 확인 |
| 플랫폼 통제 가능성 | 외부 요인 | 일부 통제 | 문토 화면·정책으로 직접 통제 |
| Sprint 2 설계 적합성 | 후속 과제 | 일부 화면에 반영 가능 | 핵심 화면으로 명확히 구체화 가능 |

총점이 높은 문제를 Sprint 2의 핵심 문제로 채택한다. 점수만으로 결정하지 않고, 제외한
문제와 이유도 함께 기록한다.

## 8. Sprint 2 진입 조건

Sprint 1.5는 다음 조건을 충족하면 완료한다.

- [ ] 실제 문토의 핵심 여정이 클럽 탐색부터 가입·비가입 결정까지 연결되어 있다.
- [ ] 각 단계의 화면과 정보 제공 상태가 캡처 또는 확인 메모로 남아 있다.
- [ ] Sprint 1 근거 카드가 현재 플로우의 문제 지점에 연결되어 있다.
- [ ] 확인된 사실과 연구자 가설이 구분되어 있다.
- [ ] 우선 문제 1개와 제외 범위가 결정되어 있다.
- [ ] Sprint 2의 핵심 시나리오가 아래 문장으로 설명된다.

> 클럽을 처음 고르는 사용자가 활동 방식과 최근 운영 이력을 비교하고,
> 자신에게 맞는 클럽을 선택하거나 근거 있게 제외한다.
