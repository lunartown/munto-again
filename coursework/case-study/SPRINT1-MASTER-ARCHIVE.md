## 1. 프로젝트 출발점

### 1.1 초기 문제 인식

취미 기반 소셜 커뮤니티가 시간이 지나며 이성 만남·술자리 중심으로 보이고, 취미 목적 사용자가 원하는 모임을 찾기 어려워져 이탈한다는 문제의식에서 시작했다.

### 1.2 초기 가설

> 소개팅 목적 모임이 증가해 취미 목적 사용자가 원하는 모임을 찾기 어렵고 이탈한다.

이 가설은 조사 주제로는 유효했지만, 처음부터 서비스 문제의 최종 정의로 확정하지 않았다.

### 1.3 초기 리서치 질문

- 취미 목적으로 소셜 커뮤니티를 사용하는 사람은 왜 이탈하는가?
- 모임을 고를 때 무엇을 보고 만남 목적이라고 판단하는가?
- 그 판단 이후 걸러냄·참여·앱 종료·이탈 중 어떤 행동을 하는가?
- 실제 소개팅성 모임은 전체의 몇 %인가? 카테고리별 편차가 있는가?
- 어떤 기능·구조가 만남 목적 유입을 촉진하는가?
- 취미 목적 사용자는 어떤 대안을 사용하는가?

## 2. 방법론 결정 과정

### 2.1 인터뷰를 포함한 이유

목록 분석은 공급 구성, 리뷰는 불만의 표현을 보여주지만, 사용자가 왜 그렇게 판단했고 무엇을 참았으며 이후 무엇으로 이동했는지는 후속 질문 없이는 확인하기 어렵다. 따라서 최소 3명 인터뷰를 제안했고, 실제로 주최자·참여자·참여자 겸 주최자를 포함한 7건으로 확장했다.

### 2.2 정량 조사

| 자료 | 범위 | 역할 |
|---|---:|---|
| 문토 모집글 | 200건 | 목적 유형과 카테고리별 공급 구조 확인 |
| Google Play 공개 리뷰 | 1,200건 시계열 | 평점·문제 표현의 시간 변화 확인 |
| Google Play 검토 리뷰 | 62개 고유 리뷰 | 반복 불만과 행동 결과 코딩 |
| App Store 검토 리뷰 | 27개 고유 리뷰 | Google Play 패턴의 교차 확인 |
| 통합 리뷰 | 89개 고유 리뷰·135개 발화 카드 | 리뷰 어피니티 정량화 |

추가 표집 기록: 최근 Google Play 리뷰 120건 중 내용 분석 대상은 119건이며, App Store 독립 표본은 50건이다. 89개 고유 리뷰·135개 카드는 실제 검토·교차분석에 사용한 정제 표본이다. 전체 `qualitative_cards.csv`에는 앱 리뷰 카드 외에 블로그·프로덕트 분석에서 만든 맥락 카드 9장이 포함되어 총 144장이다. 외부 맥락 카드는 리뷰 빈도나 리뷰 클러스터 분모에 합산하지 않는다. 서로 다른 표본을 같은 분모로 합치지 않는다.

### 2.3 정성 조사

- 익명화 인터뷰 7건
- 인터뷰 근거 카드 35장
- 모집글·앱 리뷰의 원문 발화 카드
- 원문 발화 → 태그 → AI 1차 군집 → 직접 재배치 → 근거 교차검증 순서

## 3. 모집글 분석 결정과 결과

### 3.1 코딩북

- A 순수 취미: 활동 자체가 목적
- B 사교 혼재: 취미 활동과 친목·네트워킹이 함께 존재
- C 만남 목적: 소개팅·매칭·성비 균형·이성 조건 등 직접 신호가 존재
- C 신호를 최우선으로 판정
- 애매한 경우 낮은 등급으로 보수적으로 판정

### 3.2 결과

| 기준 | A | B | C | C 비율 |
|---|---:|---:|---:|---:|
| 모집글 200건 | 76 | 60 | 64 | 32.0% |
| 고유 포맷 159건 | 62 | 47 | 50 | 31.4% |

- C 64건 중 58건이 연애 전용 카테고리 밖에 있었다.
- 파티 60.3%, 소셜게임 52.6%, 취미 3.8%로 카테고리 편차가 컸다.
- 연애 전용 카테고리 6건을 제외해도 C는 58/194건(29.9%)이었다.
- 사람 검증 표본 20건 일치율 16/20(80%)으로 사전 기준을 충족했다.

### 3.3 해석의 한계

한 시점의 `type=default` 노출 스냅샷이며, 무작위 표본이나 전체 모집단 추론이 아니다. C 비율은 공급 구조를 보여주지만 실제 사용자 이탈률을 의미하지 않는다.

## 4. 리뷰 수집·분석 결정과 결과

### 코딩 규칙

- 분석 단위는 불만 글 전체가 아니라 하나의 발화 또는 행동 증거 하나다.
- 탐색피로·숨은만남신호·기대불일치·성비·호스트상업화·안전·경험품질·이탈·대체서비스·긍정·반례 태그를 사용했다.
- 별점만 있고 발화가 없는 리뷰는 카드로 만들지 않았다.
- 원문을 확인하지 않은 검색 결과 요약문은 코딩하지 않았다.
- 같은 리뷰가 여러 주제를 말할 수 있으므로 다중 태깅을 허용했다.
- 가설을 반박하는 긍정 사례도 삭제하지 않고 반례로 남겼다.

1. 공개 리뷰 원자료 수집

## 6. 어피니티 다이어그램 과정

### 6.1 원문 근거 카드

한 카드에 관찰 하나를 두고, 인터뷰 역할과 경험 태그를 분리했다. 긍정·불편·행동·반례·안전·이탈·운영중단·니즈를 함께 남겨 부정 사례만 수집하지 않았다.

### 6.2 AI 1차 군집

AI는 의미 유사성으로 후보를 제안했을 뿐 최종 분류로 사용하지 않았다. AI 후보를 직접 재배치하고, 왜 이동했는지 근거를 남겼다.

### 6.3 직접 재분류 기준

- 참여 전 예측 조건
- 상호작용 포맷
- 호스트 운영 노동
- 안전·거버넌스
- 지속·소속감
- 앱 신뢰·사용성
- 실제 행동 결과

원인과 결과를 섞지 않기 위해 최종 재분류에서 비선택·삭제·외부 이동·운영중단은 결과 영역으로 분리했다.

### AI 사용 기록

- 질문 설계: 초기 질문의 가정을 점검하고 하위 질문을 확장했다.
- 코딩: 모집글 설명을 A/B/C로 1차 분류하고 확신도와 판정 근거를 출력했다.
- 리뷰 패턴: 키워드·감정·행동 태그 후보와 빈도표를 생성했다.
- 군집화: 유사 발화 클러스터 후보를 제안받은 뒤 사람이 재배치했다.
- 사람 검증: 모집글 20건과 리뷰 검토 표본을 원문 기준으로 다시 판정했다.

AI 결과를 최종 근거로 그대로 사용하지 않고, 원문 대조·중복 제거·태그 수정·근거 강도 조정을 거쳤다.

## 7. Fishbone·5 Whys 의사결정

### 7.1 Fishbone을 사용한 이유

어피니티 클러스터는 반복 패턴을 보여주지만 원인과 결과가 섞이기 쉽다. Fishbone으로 목적·운영 포맷·비용·안전·호스트 지원·제품 기본기를 원인 축으로 분리했다.

### 7.2 5 Whys 결과

핵심 흐름은 다음과 같다.

```text
실제 목적·진행·규칙·비용·안전 기준이 비교 가능한 약속으로 보이지 않음
→ 참여 전 실패 위험을 판단하기 어려움
→ 기대 불일치·취소·분쟁·안전 문제가 발생
→ 책임 주체와 해결 상태가 불명확함
→ 시간·비용·안전 손실을 개인이 감당하고 이탈
```

### 7.3 확정하지 않은 원인

호스트 역량 의존과 플랫폼 지원 부족은 인터뷰에서 강하게 나타났지만, 리뷰에서 독립적으로 반복된 근거는 상대적으로 적어 핵심 문제 자체가 아니라 원인 가설로 보류했다.

- 주요 사용자: 문토에서 클럽을 처음 또는 초기에 탐색하는 사람
- 주요 순간: 클럽 탐색부터 상세 비교와 가입·비가입 결정까지
- 보조 근거: 소셜링 모집글·리뷰와 문제 발생 후 보호 흐름
- 제외: 소개팅 모임 자체 제거, 문토 사업 성과 판단, 좋은 호스트 감소 주장, 추천 알고리즘 내부 의도 추정

## 9. 버리거나 보류한 판단

- “문토가 망하고 있다”는 판단: 리뷰만으로 서비스 성장·쇠퇴를 단정하지 않음
- “소개팅이 문제의 전부”라는 판단: 취미 가치가 충족된 긍정 반례가 존재함
- “퀄리티 높은 모임장이 줄었다”는 주장: 품질 기준과 공급 추세 데이터가 없어 보류
- “호스트 지원 부족이 최종 핵심 문제”라는 주장: 인터뷰 편중으로 원인 가설에 보류
- “앱 오류가 모든 이탈의 원인”이라는 주장: 오프라인 운영·안전 문제와 분리
- 기간별 리뷰만으로 현재 UX를 단정: 최신 리뷰를 중심으로 보되 시계열은 맥락으로 사용

### 10.0.1 다이어그램을 여러 번 다시 그린 이유

처음에는 소셜링만 일자형으로 그렸으나, 리서치의 주된 경험과 현재 설계 대상은 클럽에 더 가까웠다. 또한 홈·검색·카테고리·찜이 모두 실제 진입점이라는 점도 누락됐다. 현재 정본은 `클럽 목록 → 상세 → 가입 질문 → 승인 → 채팅·활동`으로 다시 잡고, 소셜링·챌린지는 각각의 확인 수준을 담은 참고 플로우로 보존한다.

### 10.1 조사 범위

정본 범위는 앱 진입, 홈, 검색, 카테고리, 찜, 클럽 목록·검색 결과, 상세, 가입 질문, 승인 대기, 가입 완료, 채팅과 정기 활동이다. 소셜링의 신청·결제·취소와 챌린지 상태는 비교·참고 범위로 분리했다.

### 10.2 플로우를 다시 그린 이유

처음에는 일자형 플로우로 단순화했지만 홈·검색·카테고리·추천·찜 등 진입점이 실제로 거미줄처럼 연결되어 있어 현재 구조를 왜곡했다. 이후 화면을 실제 페이지 단위로 두고, 선택·결정·상태 변화만 연결하는 방식으로 다시 작성했다.

### 10.3 플로우에서 확인한 문제 후보

- 클럽의 활동 목적·반복 방식·신규 멤버 참여 방식이 한눈에 비교되지 않음
- 전체 가입자 수는 보이지만 실제 활성 멤버와 최근 활동 규모를 판단하기 어려움
- 운영 규칙과 가입 후 진행 과정이 여러 영역에 흩어져 있음
- 가입 질문·승인·채팅 이후의 상태는 연결되지만, 가입 전 지속성을 판단할 근거가 약함
- 실제 정기 활동·참석·후기 상태는 캡처 근거가 제한적이므로 미확인으로 남김

### 10.4 챌린지와 미확인 상태

챌린지는 홈·상세·참여 질문·신청과 매일 인증·종료 후 티타임까지 확인했다. 다만 챌린지 전용 승인 대기·자동취소·거절 화면은 직접 캡처하지 못했다. 소셜링과 클럽에서 동일한 24시간 승인 정책 문구가 확인되고 챌린지도 승인제로 표시되지만, 챌린지 상태를 그대로 확정하지 않고 가설로 표시한다.

### 10.5 화면 증거

현재 상태 캡처 39장은 `research/data/current_state/screenshots/`에 보존했다. 확보 범위는 홈·검색·카테고리·소셜링·클럽·찜·챌린지이며, 실제 참석·체크인·후기 화면과 일부 챌린지 상태 화면은 추가 확보 대상으로 남겼다.

## 12. Figma 정리 대상

위 6개 섹션은 2026-08-03에 1920×1080 고정 슬라이드 21장으로 정리했다. 링크와 구성은 [`design/figma-index.md`](design/figma-index.md)의 "Sprint 1 Master Archive (슬라이드 정리본)" 행에 있다. 이 아카이브 문서 내용을 고치면 Figma 쪽도 같이 갱신해야 하며, 반영 여부는 그 행의 링크에서 확인한다.

| 참석·체크인·후기 완료 화면 | 미확인 | 현재 확보한 캡처 범위 밖이므로 다이어그램에 확정 상태로 넣지 않음 |

## 16. Sprint 2로 넘기는 결정 패키지

Sprint 1의 결론은 기능 확정이 아니라 다음 검증 패키지다.

### 선택된 관점

클럽을 처음 고르는 사용자가 가입 전에 실제 활동 목적과 반복 방식,
구성원 분위기, 운영 규칙과 최근 활동을 확인하고 자신에게 맞는지 판단할 수 있어야 한다.

### 기능 후보(아직 미확정)

- 가입 판단에 필요한 정보를 구조화한 클럽 프로필
- 최근 활동과 실제 활동 주기를 보여주는 이력
- 전체 가입자와 구분되는 활성 멤버·최근 참여 규모 정보
- 신규 멤버 참여 방식과 운영 규칙 요약

이 네 가지는 확정 기능 목록이 아니다. 현재 클럽 플로우의 정보 공백을 바탕으로 만든
아이디어 후보이며, 이번 과제에서는 JTBD와 대표 시나리오에 맞춰 IA·사용자 플로우·
와이어프레임으로 좁힌다. 실제 제품 지표를 통한 가설 검증은 범위에 포함하지 않는다.
